JVM 类加载机制与双亲委派：从 class 文件到可使用的类

Tianziyu-coder2025-09-202026-11-12

一句话总结

类从 class 文件到能用要经历加载 → 验证 → 准备 → 解析 → 初始化；双亲委派让类先交给父加载器，保证 java.lang.* 不被用户代码替换；而 SPI、Web 容器、热部署这三类场景必须打破它。

一、类的生命周期

阶段 做什么 容易记错的点
加载 按全限定名读字节码，生成 Class 对象 数组类由 JVM 直接创建，不走类加载器
验证 校验魔数、字节码、符号引用 -Xverify:none 可关（不推荐）
准备 为静态变量分配内存并赋零值 static int a = 1 此时 a=0，不是 1
解析 符号引用转直接引用 可以在初始化之后再解析（动态绑定）
初始化 执行 <clinit>()，赋真实值、跑静态块 JVM 加锁保证多线程下只执行一次

会触发初始化：new、读写类的静态字段（非 final 常量）、调用静态方法、反射 Class.forName、初始化子类时先初始化父类、启动类（含 main 方法）、JDK 8 起接口默认方法实现类初始化。

二、四层类加载器

加载器 负责范围 父加载器
Bootstrap $JAVA_HOME/lib 下的核心类（rt 模块化后为 jmods） 无（C++ 实现，getParent() 返回 null）
Platform（JDK 9+）/ Extension（JDK 8） 平台扩展模块 / jre/lib/ext Bootstrap
Application / System classpath 下应用自己的类 Platform
自定义 指定路径、网络、加密字节码等 Application

JDK 9 模块化把 Extension 换成 Platform ClassLoader，并调整了部分委派规则；面试按”启动 / 平台 / 应用 / 自定义”四层说即可。

类的唯一性 = 全限定类名 + 定义它的类加载器。两个不同加载器加载的同名类，instanceof / 强转会失败，这是热部署容器里 ClassCastException 的常见来源。

三、双亲委派的实现与好处

好处两条：

  1. 避免重复加载：父加载器加载过，子加载器直接复用；
  2. 保护核心类库：用户自己写一个 java.lang.String，委派会先让 Bootstrap 找到 JDK 的那个，用户类永远没机会生效（试图用自定义加载器直接 defineClass java.* 还会抛 SecurityException）。

自定义类加载器应重写 findClass 而不是 loadClass，这样不会破坏委派：

四、什么时候必须打破委派

委派的前提是”父加载器能看见所有需要的类”，但父加载器加载的代码有时反过来要调用子加载器 classpath 里的实现：

场景 矛盾 做法
JDBC / SPI DriverManager（Bootstrap 层）要加载各厂商 Driver（classpath） 用线程上下文类加载器 TCCL：Thread.currentThread().getContextClassLoader()
Tomcat 多个 WebApp 各自带不同版本的同名库，还要相互隔离 每个 WebApp 一个 WebappClassLoader，先加载自己 WEB-INF 下的类，再委派
OSGi / 热部署 / JSP 需要按模块/实例卸载与替换类 网状委派，类加载器即隔离边界

Spring Boot 的 LaunchedURLClassLoader、Dubbo 的 SPI、SLF4J 的绑定也都属于这一类思路。

注意 Class.forName(name) 默认会初始化，ClassLoader.loadClass(name) 只加载不初始化，Class.forName(name, false, loader) 可显式关闭。

五、面试怎么答

  • 双亲委派是什么、好处？ → 先委托父加载器、父不行才自己加载；避免重复加载 + 保护 JDK 核心类不被篡改。
  • 怎么打破？ → 继承 ClassLoader 重写 loadClass（谨慎），或用 TCCL 让上层代码反向调用下层实现；举 JDBC + Tomcat 为例。
  • 两个类”相同”怎么判断？ → 全限定名相同且由同一个类加载器定义，否则连强转都不行。
  • ClassNotFoundException 和 NoClassDefFoundError？ → 前者是加载时按名找不到 class 文件（检查型异常）；后者是编译时存在、运行时找不到或初始化失败（Error），常见于打包漏依赖、静态块抛异常。

六、踩坑清单

  1. 自定义加载器尽量只重写 findClass，别动 loadClass 的委派链；
  2. 热部署后旧加载器没被回收 = 元空间泄漏，注意静态引用、线程 TCCL、定时任务；
  3. 依赖冲突时先看 ClassLoader.getResource() / -verbose:class 确认类到底从哪个 jar 加载；
  4. JDK 9+ 反射访问 JDK 内部类会被模块系统拦住，别再靠 --add-opens 硬解，优先换公开 API；
  5. static final 常量被编译期内联，改了常量值却只重发一个 jar，调用方不重新编译就不会更新。
