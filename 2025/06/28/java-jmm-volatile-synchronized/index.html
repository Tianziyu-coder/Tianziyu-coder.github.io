JMM、volatile 与 synchronized：可见性、原子性、有序性

Tianziyu-coder2025-06-282026-11-12

一句话总结

并发三问题：可见性（缓存/工作内存）、原子性（复合操作被打断）、有序性（指令重排序）。volatile 解决可见性与有序性但不保证原子性；synchronized 三个都解决，代价是互斥。

一、JMM 与 happens-before

JMM 规定：所有变量存在主内存，每个线程有自己的工作内存（可理解为 CPU 缓存/寄存器抽象），线程读写变量要先与工作内存交互，再由 JMM 控制何时同步回主内存。

happens-before 是判断”一个线程的写对另一个线程是否可见”的规则，不依赖具体 CPU 内存模型：

规则 含义
程序顺序 单线程内，前面的操作 happens-before 后面的操作
volatile 变量 对 volatile 的写 happens-before 后续对它的读
监视器锁 解锁 happens-before 之后对同一把锁的加锁
线程启动 / 终止 start() 之前的操作对新线程可见；线程结束前的操作对 join() 之后可见
传递性 A hb B、B hb C ⇒ A hb C

没有 volatile，ready 和 x 的写入可能被重排序或停留在缓存里，断言随时可能失败。

二、volatile 的两个语义

  1. 可见性：写立即刷新到主内存，读会使工作内存中该变量失效；
  2. 禁止指令重排序：编译器/JIT 在 volatile 写前插入 StoreStore、写后插入 StoreLoad 屏障，在读前后插入 LoadLoad / LoadStore 屏障。

不保证原子性是最常见的误解：

volatile 只保证每次读写都看到最新值，但多个线程可能同时读到同一个值再各自 +1，结果照样丢更新。要原子性得用 AtomicInteger（CAS）、LongAdder 或加锁。

适用场景很窄：状态标志、一次性安全发布、DCL 单例。

new Singleton() 分三步：分配内存 → 初始化对象 → 把引用赋给 instance。若不加 volatile，步骤 2、3 可能重排序，另一个线程在第一次判空时拿到非 null 但未初始化的对象。volatile 的写屏障挡住了这个重排序。

三、synchronized 与锁升级

synchronized 编译成 monitorenter / monitorexit，底层是对象头 Mark Word 指向的 Monitor。它是可重入的（同一线程重复加锁不会自锁），并且解锁时会把所有修改刷回主内存，因此天然保证可见性与原子性。

HotSpot 为降低无竞争时的开销做了锁升级：

状态 触发 实现
无锁 无线程竞争 普通对象
偏向锁 长期只有一个线程进入 Mark Word 记线程 ID，几乎零成本
轻量级锁 有第二个线程交替进入（无实际并发） CAS + 栈上 Lock Record，自旋
重量级锁 自旋失败 / 真正并发竞争 挂到 Monitor 的阻塞队列，线程挂起唤醒

JDK 15 起偏向锁默认关闭并已弃用（JEP 374），因为它在大并发场景下的撤销成本常常得不偿失。面试答出”升级路线 + 偏向锁现状”比背四态更显版本意识。

与 ReentrantLock 的取舍：

synchronized ReentrantLock
释放 JVM 自动 必须 finally { unlock(); }
可中断 否 lockInterruptibly()
公平锁 否 可构造公平锁（吞吐更低）
条件队列 一个（wait/notify） 多个 Condition
尝试加锁 否 tryLock()

绝大多数业务代码用 synchronized 就够了，别为了”更灵活”引入忘记解锁的风险。

四、面试怎么答

  • volatile 和 synchronized 的区别？ → volatile 轻量、只保证可见性与有序性，不能保证复合操作原子性，也不会阻塞线程；synchronized 是互斥锁，三者都保证，有上下文切换成本。
  • volatile 能保证原子性吗？ → 对单次读写可以（含 long/double 在 64 位 JVM 上的原子性保证），对 i++、先检查再执行这类复合操作不行。
  • DCL 单例为什么要 volatile？ → 防止对象引用赋值与初始化重排序，避免其他线程拿到未初始化对象。
  • synchronized 锁的是什么？ → 修饰实例方法锁 this，静态方法锁 Class 对象，代码块锁括号里的对象。锁对象本身要稳定，用 synchronized(new Object()) 等于没锁。

五、踩坑清单

  1. 别锁字符串常量或 Integer 缓存对象：它们被 JVM/常量池共享，两个不相干的业务会互相阻塞，甚至死锁；
  2. volatile 修饰的是引用，不是对象内部字段：volatile List<String> list 只保证 list 引用可见，往里 add 依然不安全；
  3. volatile 数组同理，只保证数组引用可见，元素读写要用 AtomicReferenceArray；
  4. 状态标志用 volatile 可以，但”检查后再执行”（if-then-act）的逻辑必须加锁或用 CAS；
  5. 双重检查里两次判空都不能省：少第一次会每次加锁，少第二次会创建多个实例；
  6. 锁粒度别包住远程调用/数据库操作，持锁时间越长越容易把线程池打满。
