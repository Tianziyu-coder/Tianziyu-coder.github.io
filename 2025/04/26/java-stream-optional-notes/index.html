Stream 与 Optional 实战：好用，但别用错

Tianziyu-coder2025-04-262026-11-12

一句话总结

Stream 是不存数据、一次性消费、惰性求值的计算管道；Optional 是给方法返回值表达”可能没有”的容器，不是用来替代所有 null 判断的。两者用对了代码更短，用错了更容易踩坑。

一、Stream 的三条基本性质

  1. 不存储数据：只持有数据源的引用，结果要靠 collect 收出来；
  2. 惰性：中间操作在终端操作之前不会执行，所以 stream().filter(...) 单独写一行等于什么都没做；
  3. 一次性：终端操作后流已关闭，再次遍历抛 IllegalStateException: stream has already been operated upon or closed。
类型 常见方法
中间（返回 Stream） filter map flatMap distinct sorted peek limit skip
终端（返回结果） collect forEach toList count reduce anyMatch allMatch findFirst findAny

peek 只在调试时用（且必须接终端操作才会执行），别用它做业务赋值。

三、parallelStream 不是”加个 parallel 就变快”

适用判断：

  • 数据源可拆分（ArrayList、IntStream.range 好，LinkedList、IO 流差）；
  • 任务量大且单个元素处理偏 CPU 密集，小集合的拆分支配/合并开销反而更慢；
  • 无共享可变状态、无顺序依赖、无 IO/数据库调用（并行会打满公共 ForkJoinPool，把别的服务拖慢）；
  • 需要有序结果时别用 forEach（forEachOrdered 会抵消大部分并行收益）。

线上服务里更该谨慎：Web 请求本身已经并发，再套 parallelStream 抢的是同一个公共池。

四、Optional 的正确用法

orElse 与 orElseGet 的区别是高频题：

orElse 的参数是先求值再传进去的，如果里面是远程调用/查库，代价很实在。

Optional.get() 不先判断 空值时抛 NoSuchElementException，等于换了个 NPE

五、性能与可读性

Stream 有 lambda、装箱、函数对象等开销，几十个元素的简单循环里手写 for 通常更快，但差距在微基准之外基本可以忽略。取舍标准是可读性：多步过滤/映射/分组用 Stream 明显更清晰；带 break、多重下标、需要修改外部状态的逻辑用循环更直接。

六、面试怎么答

  • 什么是惰性求值？ → 中间操作只构建管道，终端操作才触发遍历；好处是可以做短路（findFirst、anyMatch）和循环融合，避免多次遍历。
  • findFirst 和 findAny 区别？ → 前者保证按 encounter order 返回第一个，后者在并行流里可返回任意一个以换取性能；串行流下通常结果一样，但不要依赖。
  • reduce 与 collect 区别？ → reduce 把元素归约成一个不可变结果（如求和），collect 用可变容器累加，适合收集成集合/Map。
  • orElse 和 orElseGet？ → 前者参数无论是否为空都会求值，后者惰性。

七、踩坑清单

  1. Stream 别存成字段反复用，用完即弃；
  2. Collectors.toMap 一律显式处理重复 key；
  3. parallelStream 里别碰共享集合、别查数据库；
  4. map 返回 null 会让后续 collect 或 toMap 炸掉，先 filter(Objects::nonNull)；
  5. 基本类型流用 IntStream / LongStream 避免装箱，sum() 比 reduce(0, Integer::sum) 更直白；
  6. Optional 不要用在 DTO/JSON 序列化上，Jackson 需要额外模块才能正确处理。
