String、字符串常量池与 StringBuilder：一篇讲透

Tianziyu-coder2025-02-182026-11-12

一句话总结

String 是不可变的 final 类；字面量进字符串常量池复用，new String(...) 一定在堆上新建对象；JDK 9 之后底层从 char[] 换成 byte[] + coder；循环拼接必须用 StringBuilder。

一、String 为什么不可变

三点保证：类 final 不能被继承改写、内部数组 private final 且不外泄、没有提供任何修改 value 的方法。连 substring / replace 都是返回新对象。

不可变带来的好处：

好处 说明
线程安全 无需同步就能在多线程间共享
可缓存 hash hashCode() 只算一次，所以适合做 HashMap 的 key
常量池复用 相同字面量指向同一对象，省内存
安全 类加载名、URL、数据库用户名传进去不会被中途改动

反射确实能改 value，但那属于破坏封装，模块化 JDK 下还要 --add-opens，面试别拿这个当”String 可变”的论据。

二、常量池：== 到底比什么

new String("abc") 创建了几个对象？两个（如果池里还没有 "abc"）：字面量触发入池一个对象，new 再在堆上创建一个；如果池里已有，就只有堆上那一个。

常量池位置的演进是常考点：

JDK 字符串常量池位置 关键变化
6 方法区（永久代） intern() 会把字符串复制一份到永久代
7 堆 intern() 改为记录堆中首次出现的引用，不再复制
8 及以后 堆 永久代被元空间取代，但字符串常量池仍在堆里

JDK 7 这个改动直接影响一道经典题：先 new String 再 intern()，JDK 6 下 == 为 false（两个不同对象），JDK 7+ 为 true（池里存的就是堆对象引用）。

三、编译期优化与拼接

JDK 8 把变量拼接编译成 new StringBuilder().append(...).toString()；JDK 9 之后改用 invokedynamic + StringConcatFactory，避免每次都生成固定的 StringBuilder 字节码，为后续优化留空间。

真正的坑在循环里：

StringBuilder StringBuffer
线程安全 否 是（方法加 synchronized）
性能 更高 略低
适用场景 方法内局部拼接（绝大多数） 确实存在多线程共享写入时才用

单线程局部变量的拼接用 StringBuffer 属于无意义加锁，看到就该改掉。

四、JDK 9 的紧凑字符串

JDK 8 的 char[] 每个字符固定 2 字节。JDK 9 起改成 byte[] + coder：内容全是 Latin-1 就用 1 字节/字符，含中文等再用 UTF-16 的 2 字节。纯英文/数字为主的场景能省近一半堆内存——这对大量缓存 key、日志字符串的服务很实在。String 的公开 API 完全没变，所以业务代码无感。

五、面试怎么答

  • String 为什么设计成不可变？ → 线程安全、可缓存 hash（适合做 HashMap key）、常量池复用、作为参数传递不会被篡改。
  • == 与 equals 区别？ → == 比引用（基本类型比值），equals 被 String 重写为逐字符比内容。比较字符串内容一律用 equals。
  • StringBuilder 为什么比 + 快？ → + 在循环里每次生成新对象；StringBuilder 在可扩容数组上原地 append。补一句 JDK 9 的 invokedynamic，能显出版本意识。
  • intern() 有什么用、有什么风险？ → 把字符串纳入池复用，适合大量重复值（如省市名）省内存；但池在堆里、受 GC 管理，滥用会让大量长生命周期引用滞留，且调用本身有哈希表开销。

六、踩坑清单

  1. null 参与 + 拼接会得到字符串 "null"，不会抛异常，容易把脏数据写进库；
  2. 常量调 equals："ACTIVE".equals(status)，别写成 status.equals("ACTIVE")；
  3. split 参数是正则，按点分割要写 str.split("\\.")；
  4. String 不可变，密码这类敏感内容用完无法清零，安全场景用 char[] 并主动 Arrays.fill；
  5. substring 在 JDK 6 会共享原 char[] 导致大字符串无法回收，JDK 7+ 已改为复制，属于历史问题，别再当成现行结论；
  6. 别用 new String(bytes) 不指定字符集，平台默认编码不一致会乱码，统一 StandardCharsets.UTF_8。
